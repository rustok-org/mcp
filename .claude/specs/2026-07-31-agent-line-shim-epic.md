# Эпик: полный шим `rustok` для агентской линии

> Статус: **ПЛАН, до `/check`.** Кода нет. Соло-режим.
> Триггер: бэклог Ф-4 «опция — шим для агентской линии» + прямой запрос Капитана «напиши
> подробный план, бери за референс TUI».
> Референс: `cli/rustok` (main, консольная линия, **1297 строк**, живой, поставленный шим —
> не старый эпик-документ, а реально доставленный код) + эпик
> `.claude/specs/2026-07-16-rustok-easy-install-epic.md` (для решений/инвариантов).

## Уже готово — важно прочитать перед стадиями ниже

Часть того, что консольному эпику пришлось строить с нуля, **уже сделано для агентской линии
предыдущими кругами** — эпик их не переделывает, только использует:

- **Secret-гигиена (Ф-3, `1c01418`):** entrypoint агентской линии уже принимает
  `RUSTOK_KEYRING_PASSWORD_FILE` (podman `type=mount`/docker bind-mount), `-e` всегда
  побеждает, именованные ошибки вместо 60-с виса. Шиму нужно только **правильно вызывать**
  то, что уже есть — ядро не трогаем.
- **Движко-нейтральная декларация (Ф-4, `411b3cb`/`73e661a`):** `requires.anyBins:[docker,
  podman]`, `ENGINE`-конфиг в `smithery.yaml`.
- **Протокол/хэндшейк (Ф-1, `9de501f`):** современные MCP-клиенты подключаются.
- **Честный ClawHub-листинг (Ф-2 + два security-audit follow-up'а, `73e661a`):** текст
  соответствует реальному образу, живой скан подтверждён.

Итого: эпик ниже — **не «сделать безопасную доставку пароля»** (уже есть), а **«обернуть уже
рабочий механизм в одну команду»**.

## Разбор `cli/rustok` (main) — что портируем как есть, что режем, что переписываем

Прочитал файл целиком (1297 строк, POSIX `sh`). Функции по группам:

### 1:1 порт, без изменений по сути (движко-агностичный код)
`resolve_engine`, `discover_ids`, `agent_of`, `agent_list`, `volume_for`, `valid_agent_name`,
`secret_for`, `password_file_for`, `secret_present`, `rustok_env_names`, `rpc_env_names`,
`rpc_secret_names`, `label_volume_args`, `rpc_secret_args`, `store_rpc_secrets`,
`read_password_twice`, `store_password`, `remove_stored_password`. Единственная правка везде —
`image_ref`/`DEFAULT_IMAGE`: `ghcr.io/rustok-org/rustok-wallet` вместо `-tui`.

### 1:1 порт с точечной правкой текста (не логики)
- `cmd_init` — единственная строка требует правки: комментарий/сообщение «prints the 12-word
  phrase and approval PIN exactly once» → «prints the 24-word phrase exactly once» (агентское
  ядро PIN не печатает вообще — approval-механизма нет). Сама механика (создание secret/
  файла, вызов `create-wallet`, one-shot `-it`) не меняется.
- `wallet_run_args`, `start_wallet_detached`, `cmd_start`, `cmd_stop` — логика полностью
  движко/продукто-агностична (просто запуск контейнера с нужными флагами); проверить, что
  `image_ref`/лейблы подставляются верно, семантических правок не требуется.
- `cmd_status` — 1:1, диагностика движка/PATH/config не завязана на approval.
- `cmd_update` — 1:1.

### Требует построчной сверки на этапе кода (найдено `/check`'ом, не «1:1», как я сперва решил)
- `cmd_connect` (516-662) + `connect_write_claude`/`connect_write_cursor`/`connect_write_hermes`
  (663-784, ~270 строк суммарно) — по беглому чтению в основном код записи MCP-конфига
  клиента, НО строка 572-573 содержит `-tui`-специфичное предупреждение («doc-era
  rustok-wallet-tui запись обнаружена»); либо адаптировать под агентский эквивалент (если он
  есть), либо убрать за неприменимостью.
- `cmd_doctor` (805-862) — строка 856 ищет осиротевший контейнер с фиксированным именем
  `rustok-wallet-tui` (легаси до label-модели); агентская линия никогда не использовала
  `--name`, так что либо этот кусок неприменим и удаляется, либо нужен свой legacy-паттерн —
  уточнить при кодировании.
- `cmd_uninstall` (973+) — строка 981, тот же паттерн в списке томов при поиске томов на
  удаление.

### Полностью убрать (нет смысла — approval-консоли не существует)
`cmd_console` (строки 474-516, ~42 строки) — весь блок: exec-or-start, поллинг
`/run/wallet/approve.sock` (агентское ядро такой сокет не создаёт вообще), `rustok-console`
внутри образа (бинаря нет в `rustok-wallet`, только в `-tui`). Дефолтная команда без
аргумента (сейчас `console`) должна стать чем-то другим — `help` или `status` (решение ниже).

## Цель

`curl | sh` ставит шим `rustok` (или другое имя — решение ниже) в `~/.local/bin`; дальше
`rustok init` / `start` / `stop` / `connect claude|cursor|hermes` / `status` / `doctor` /
`update` / `uninstall` — без единой ручной команды `docker run`/`podman run` и без ручного
редактирования MCP-JSON. Никакой approval-консоли — агентская линия ей не пользуется.

## Компоненты/стадии → PR

Нумерация продолжает бэклог аудита (следующий свободный — Ф-9 занят, начинаю с Ф-10; финальный
номер — на усмотрение при заведении).

### Стадия A — ядро шима (движок, дискавери, secret-плюмбинг)
- **PR-A1:** `mcp/cli/rustok` (новый файл — не трогаем консольный) — блок «1:1 порт» выше,
  `DEFAULT_IMAGE`+usage без `console`. Тесты: shellcheck + bats на стабах (по образцу
  консольной Стадии 2, PR-2.1).

### Стадия B — жизненный цикл (init/start/stop, без console)
- **PR-B1:** `cmd_init`/`wallet_run_args`/`start_wallet_detached`/`cmd_start`/`cmd_stop`.
  Тесты: e2e на podman (docker — manually probed only, тот же паттерн, что везде на этой
  линии) — red (против пустого шима) → green; строгий ассерт «24 words» в выводе
  `create-wallet`, не «12 + PIN».

### Стадия C — подключение к клиентам
- **PR-C1:** `cmd_connect`+`connect_write_claude` — точный JSON-ассерт (по прецеденту
  консольного PR-2.3a), `claude mcp list → Connected`.
- **PR-C2:** `connect_write_cursor`+`connect_write_hermes` (если реально нужны для агентской
  линии — Hermes-кейс был специфичен для консольной, уточнить у Капитана перед стартом стадии).

### Стадия D — диагностика и обслуживание
- **PR-D1:** `cmd_status`/`cmd_doctor`/`cmd_update`/`cmd_uninstall` (data-safe: том без
  `--purge-keys` не трогается).

### Стадия E — supply-chain (install.sh + подпись)
- **PR-E1:** `scripts/install.sh` агентской линии — сейчас 28-строчный «печатальщик команд»
  (находка 1.3 аудита) → полноценный установщик по образцу консольного: digest-pin pull,
  опциональная cosign-верификация (не блокирует установку при отсутствии cosign, блокирует
  при провале верификации), установка шима в PATH, инвариант «install.sh никогда не трогает
  secret/keystore» (тот же эпик-инвариант #1).
- **PR-E2:** cosign-подпись в `wallet-publish.yml` агентской линии (сейчас — `workflow_dispatch`-
  скаффолд, ручной билд, как и у консольной до её Стадии 3). **Предусловие (ops Капитана):**
  тот же блокер, что был у консольной — `rustok-core` пакет должен стать читаемым для CI, иначе
  билд упадёт на `FROM` с 403.

### Стадия F — доки и релиз
- **PR-F1:** переписать `SKILL.md`/`INSTALL.md`/`TROUBLESHOOTING.md`/лендинг под
  one-command-модель (по образцу консольного PR-4.1) — «inspect-before-run», без ручных
  `docker run`-простыней.
- **PR-F2:** релиз-поезд (тег, образ, ClawHub, Registry) — тот же паттерн, что все предыдущие
  Ф-круги.

## Решения — часть предрешена, часть требует ответа Капитана

1. **Дословный порт, где применимо** — низкий риск, логика уже проверена на консольной линии
   живой e2e-сюитой (то же обоснование, что во всех прошлых кругах).
2. ⚠️ **Требует ответа: имя шима.** Консольный шим уже называется `rustok` и ставится в
   `~/.local/bin`. Если пользователь захочет поставить **оба** продукта (агентский +
   консольный) на одну машину — конфликт: два разных бинаря с одним именем. Варианты:
   (a) один и тот же `rustok`, но с флагом/детекцией образа (`--image`/переменная), (b) отдельное
   имя команды для агентской линии (`rustok-agent`?), (c) считать это не-проблемой (по факту
   у пользователя стоит либо один продукт, либо другой — редкий кейс держать оба). Precedent
   консольной линии тут не помогает — она первая застолбила имя.
3. **24 слова — не пересматриваем** (уже решено, Ф-5.4 бэклога аудита).
4. **`install.sh` — свой тег-namespace** `wallet-vX.Y.Z` (не `wallet-tui-vX.Y.Z`), тот же
   raw.githubusercontent.com-паттерн.
5. ⚠️ **Требует ответа: нужен ли `connect hermes` для агентской линии вообще** — консольная
   версия появилась из-за конкретного инцидента (Hermes видел кошелёк неправильно). Нет
   свидетельств, что агентскую линию кто-то подключал к Hermes — можно отложить в Стадию C
   как опциональный PR-C2, не блокирующий остальное.
6. **Дефолт-команда без аргумента (был недосказан, `/check` поймал):** `usage`/help, НЕ
   `status` — молчаливое угадывание намерения хуже честного «покажи все команды»; пользователь
   не путает «шим сам решил, что мне нужно» с «шим ждёт от меня команду».
7. **Отдельный файл vs один шим с флагом продукта (явный trade-off, не молчим о цене):**
   выбираю отдельный файл — ~900 строк дублирования, но соответствует паттерну изоляции,
   который команда системно держала весь этот аудит-цикл (разные образы, разные
   ClawHub-листинги, разные git-тег-неймспейсы — ни разу не объединяли ради DRY). Один общий
   шим был бы компактнее, но означал бы трогать УЖЕ рабочий консольный `cli/rustok` ради
   нового продукта — риск регресса в живом коде против цены дублирования. Капитан может
   пересмотреть, если приоритет — компактность, а не изоляция.

## Скоуп — явно НЕ входит

- macOS/Apple Silicon/Homebrew-tap — тот же fast-follow, что у консольной (Стадия 5 там).
- Approval-консоль — не откладываем, а **исключаем принципиально**: у этой линии её нет и не
  будет (ADR, полная автономия).
- Любые изменения `core` (Rust) — шим работает поверх уже существующих env-переменных
  entrypoint'а, ничего нового от ядра не требуется.
- Windows, GUI.

## Тест-план (сквозной, по прецеденту консольного эпика)

«pty против образа» необходимо, но недостаточно — каждая PR-спека должна нести строгие
ассерты: точный JSON/YAML в клиентском конфиге, `claude mcp list → Connected`, негативные
контроли (нет secret → именованная ошибка, N>1 контейнеров без `--agent` → именованная ошибка
со списком, RPC-ключ отсутствует в конфиге агента при podman-secret-пути). Классы: shell
(shellcheck+bats), e2e (podman live, docker — manually probed only), supply-chain (`cosign
verify` в CI, Стадия E), доки (греп-инварианты).

## Definition of Done

`curl|sh` ставит `rustok` (агентская сборка); полный цикл `init → connect → start → stop →
update → uninstall` без approval-консоли на чистой Linux-машине; образ подписан+запиннен;
доки переписаны под one-command; листинги на новой версии; бэклог аудита: Ф-4 (шим-часть)
closed.

## Оценка объёма (честно, не преуменьшая)

Прямого переиспользования кода — потенциально **900+ из 1297 строк** консольного шима почти
без правок (движок/дискавери/secret-плюмбинг/lifecycle/предположительно connect). Единственный
однозначно вырезаемый блок — `cmd_console` (~42 строки). Это **меньше**, чем консольной линии
пришлось строить с нуля — но не «один вечер»: 6 стадий, ~10 PR, новая e2e-сюита под агентскую
линию (по объёму сравнимая с тем, что уже сделали в Ф-3), install.sh+cosign с нуля для этой
линии, плюс два открытых архитектурных вопроса выше (имя шима, нужен ли hermes-connect),
которые нужно закрыть до старта Стадии A/C соответственно.

## Риски / что остаётся человеку

Не автоматизируем: ввод и офлайн-бэкап 24-словной фразы (та же честная граница, что у
консольной линии — «shim ends where custody begins»). `curl|sh`-риск — тот же набор мер, что
уже приняты и проверены (digest-пин, опциональный cosign, инвариант «install.sh не трогает
secret/keystore»), не изобретаем заново.
