## ⛔ СТАТУС ПОСЛЕ АДВЕРСАРИАЛЬНОГО РЕВЬЮ (2026-08-02): НА ДОРАБОТКУ, НЕ В КОД

Четыре ревьюера (3× Sonnet по линзам «архитектурные дыры / атаки / миграция» + 1× Fable
«тот ли это план»). Ниже — только то, что **я проверил лично командой**, не со слов:

1. **«Паспорт по ядру» не работает.** Живой прогон (podman 5.8.4, этой машины): сейф под
   uid 1002; законный агент `--user 1001` и **посторонний контейнер другого образа**, тоже
   `--user 1001` — оба получили подпись, `SO_PEERCRED` неразличим. uid внутри контейнера —
   параметр командной строки атакующего, не факт о законности. **Реальная граница =
   учётная запись хост-пользователя, ровно там же, где была до рефакторинга.**
2. **Экономический провал confused-deputy (главное).** Для кошелька без лимитов «попросить
   подпись» = «забрать всё». Сейф защищает **ключ**, а не **баланс**. Против живого
   противника внутри машины выигрыш сводится к «сид не унесут на будущее», деньги уходят
   сейчас.
3. **Названа не та угроза.** Тотальный выигрыш — против массовых сборщиков секретов
   (черви, грепающие `.env`/`/proc/environ`, украденные бэкапы тома): они не реализуют наш
   сокет-протокол. Но §8 сама признаёт, что кражу файлов Фазы 1-2 не меняют («лечится
   Фазой 3 / TPM»). ⇒ **80% ценности даёт честная Фаза 0 + TPM-тир K2 из ADR — дни,
   а не квартал.**
4. **Фаза 0 — не «2 строки».** Проверено: в `core` ноль вхождений `prctl`/`libc`/`nix`
   (`PR_SET_DUMPABLE=0` поставить нечем, из POSIX sh ребёнку — нельзя), а
   `/proc/sys/kernel/yama/ptrace_scope` = **0** на этой машине, и Yama — хостовый sysctl,
   не namespaced ⇒ продукт из контейнера его не доставит. Нужен exec-wrapper +
   документированная зависимость от хоста.
5. **Фаза 1 теряет работающую защиту.** Проверено: `execute_send` физически требует
   валидный `preview_id` (`grpc/src/server.rs:224-233`), а превью выдаётся только если
   txguard не вернул `Block` (`router/src/preview.rs:59-83`). В новой схеме взломанный
   домен A идёт к сейфу напрямую — txguard становится рекомендацией. Плюс уже отгруженный
   человеческий PIN-гейт (`core/crates/grpc/src/approver.rs`, 1608 строк) оказывается на
   недоверенной стороне и обнуляется.
6. **Бюджет TCB израсходован до первой строки.** Проверено: `keyring` 665 + `crypto` 985 +
   `sign` 550 = **2200**; с `txguard` (1391, если переезжает по п.5) = **3591**. Обещание
   «1500–3000 строк, читается за вечер» недостижимо.
7. **`sign_typed_data` уже принимает два готовых 32-байтных хеша**
   (`gateway/src/lib.rs:427-428`) — прямое противоречие правилу «не подписывать вслепую».
8. **Утверждение о вакууме в каталоге MCP — ложь** (см. §9Б, исправлено).

**Прочие подтверждённые ревьюерами дыры (не проверял лично):** доставка секрета в
безсетевой автозапускаемый сейф логически невозможна без TPM (три требования
несовместимы); путь к потере средств при миграции (импорт кейстора не описан, описано
только создание); слова «откат» в 61 КБ нет ни разу; инсталлятора агентской линии не
существует (`scripts/install.sh` только печатает команды); `--network none` не закрывает
эксфильтрацию через общий том; `memfd_secret` бесполезен против снапшота гипервизора
(macOS/облако — наши площадки); гонка за владение каталогом тома; нет пиннинга образа
(downgrade-атака); канарейку §9А может задеть сам агент под инъекцией (denial-of-funds);
граф компонентов описан трижды по-разному, `core` в нём отсутствует; протокол насквозь
Ethereum-специфичен при заявленной универсальности; сроки занижены (реалистично 4–6
месяцев до 900 установок с миграцией и откатом).

**Развилка, которую я предъявил Капитану неполной:** вариант «отдельный контейнер, но
**эфемерный**» не рассматривался вовсе. Он даёт цель Фазы 1 (взлом приёмной не даёт сид)
и снимает разом доставку секрета после ребута, автозапуск, linger, миграцию жизненного
цикла и половину платформенных проблем. Требует переголосования.

**Рекомендуемая переочерёдность (см. финальный разбор в чате):** честная Фаза 0 → правка
README/спеки → воронка (шим B2 + arm64 B5 + RPC-дефолт B3) → TPM-тир K2 → и только потом
подписант, переспроектированный вокруг **эфемерного отзываемого гранта на подпись**
(ограничение по времени и отзывности, а не по сумме — совместимо с «без лимитов» и с
доктриной NVIDIA про token broker).

## 1. Переформулировка задачи

Капитан: *«агент подтверждает, что это именно он — и открывает сейф без пароля»* и
*«разбить кошелёк на части, которые не могут друг к другу залезть»*.

Это одна задача, а не две. «Паспорт» требует **проверяющего, который доверенней
предъявителя** — иначе вор проверит себя сам. Проверяющий обязан быть отдельной,
изолированной частью, у которой есть ключ и нет ничего лишнего. То есть:

> **Не «агент открывает сейф», а «сейф сам решает, подписать ли просьбу агента»** —
> ключ не выдаётся никому и никогда, наружу выходят только готовые подписи.

Это модель ssh-agent (ключ не покидает хранителя), Android Keystore (приложение
только просит операцию), Clef (внешний подписант для go-ethereum) — и, в пределе,
seL4 (крошечное доверенное ядро + изолированные домены + явные каналы).

## 2. Диагноз: что не так сегодня (проверено в коде)

| Находка | Где | Следствие |
|---|---|---|
| Пароль экспортируется **всем** процессам контейнера | `scripts/rustok-wallet-entrypoint.sh:35` (+ `-e`/podman-secret путь), дети наследуют env | Python-MCP, жующий недоверенный ввод, держит пароль в своём `/proc/self/environ` |
| Пароль реально нужен **только core и только один раз** | `core/crates/grpc/src/main.rs:69-71` — `password()` → `core.unlock()` при старте; в `crates/gateway/src/` и в `src/` (python) — **0 вхождений** | Утечка на две трети избыточна: её можно убрать без единого структурного изменения |
| Все процессы — один uid 1000 | `Dockerfile.wallet:45,66` (`USER rustok`) | ОС не мешает Python читать файлы кейстора и память core: границы нарисованы, но не построены |
| Расшифрованный ключ живёт в памяти большого сетевого процесса | `crates/wallet/src/core.rs:130,167` — core держит unlocked signer и он же ходит в RPC | Периметр доверия = весь core, а не «маленький сейф» |
| Наш собственный код это признаёт | `crates/wallet/src/unlock.rs:15-17`: *«The password is visible to processes running as the same user»* | Слабость известна, зафиксирована в доке, не закрыта |

**Вывод:** сегодня компрометация приёмной (Python/MCP-слой, поверхность prompt-injection
и чужих RPC-ответов) = кража сида навсегда и молча. Цель дизайна — превратить это в
«вор может только просить подписи, пока он резидентен, и каждая просьба видна on-chain».

## 3. Что берём у seL4 (8 принципов и их перевод)

seL4 — ядро ~10 kSLOC с машинно-проверенным доказательством соответствия спецификации
(Isabelle/HOL; whitepaper Rev 1.4.1, 2026-07-17). Доказаны confidentiality/integrity/
availability **при явных допущениях**; НЕ покрыты тайминг-каналы (Spectre-класс), DMA,
multicore, boot-код; binary-level верификация — только ARM и RISC-V. Их же FAQ:
*«If I run seL4, is my system secure? Not automatically, no.»* Мы заимствуем **дисциплину**,
не ярлык.

| # | Принцип seL4 | Перевод в наш Linux-контейнер |
|---|---|---|
| 1 | **No ambient authority**: право = только явно вручённая capability, не «у тебя такой UID» | Подписант получает при спавне только: FD кейстора, FD сокета, ничего больше. Приёмная не получает **ничего**, кроме FD канала к подписанту |
| 2 | **Confused deputy / «no designation without authority»** | На каждой границе спрашиваем: «если этот компонент полностью взломан — что максимум он может, имея только явно выданные ему ручки?» Ответ для приёмной должен быть: «попросить подпись», не «прочитать кейстор» |
| 3 | **Малый TCB** (10 kSLOC против 20 MSLOC Linux) | Подписант должен читаться человеком целиком за вечер. Реалистичный размер — **1500–3000 строк** (замеры зрелых аналогов: `ssh-agent.c` 2646, один seccomp-фильтр OpenSSH 567), не «пара сотен», как я оценил на глаз ранее |
| 4 | **Статический граф компонентов** (Microkit SDF: «no interactions beyond those defined») | Граф фиксируется до кода: `mcp → gateway → signer`. Каждое ребро — один unix-сокет с фиксированной схемой. Ничего вне графа |
| 5 | **Два дисциплинированных примитива** вместо «произвольного IPC» | Только `sign(request) → signature \| reject` (синхронно, фиксированная схема) + notify-канал обратно. Никакого двустороннего стриминга |
| 6 | **Attenuated, revocable delegation** (mint/revoke: права можно только урезать) | Естественный дом для будущих opt-in ограничений: краткоживущий отзываемый ордер вместо «подпиши что угодно». **Сегодня — не включаем** (см. §10) |
| 7 | **Availability тоже изолируется** (scheduling-context как capability) | cgroups/rate-limit на приёмную, чтобы зациклившийся tool-loop не заморил подписанта |
| 8 | **Incremental cyber-retrofit, не big-bang** (DARPA HACMS: вертолёт Boeing ULB — red team, 6 недель, полный доступ к исходникам, **0 успешных атак**; взломщики владели Linux-VM, но не вырвались) | Наша дорожная карта §7: сначала обернуть, потом вынести самое недоверенное, потом изолировать ключ. Ровно порядок HACMS |

**Родословная (красивый и верный факт):** Secure Enclave во всех современных iPhone/Mac
работает на sepOS — микроядре семейства L4 (Apple: *«runs an Apple-customized version of
the L4 microkernel»*), сестринской ветке seL4 из той же лаборатории NICTA/UNSW. То есть
индустриальный «паспорт в чипе» и «доказанное микроядро» — одна архитектурная линия.
Оговорка для честности: sepOS — **родственник** seL4, а не сам верифицированный seL4.

**Честный отрицательный результат:** кошелька/HSM/подписанта на seL4 не существует ни у
кого (проверены seL4 Foundation, Tropic Square, Zymbit, Kry10, HENSOLDT). seL4 как ОС нам
не подходит — это не контейнерный рантайм; он для нас источник принципов сейчас и,
возможно, отдельное «устройство-подписант» когда-нибудь (§7, Фаза 4).

```
│ ввод LLM-клиента, ответы чужих RPC.                      │

                        │ единственный канал:
                        │ AF_UNIX, схема sign(req)→sig|reject
┌───────────────────────▼──── ДОМЕН B: подписант (uid 1002) ┐
│ rustok-signer, ~1500-3000 строк, читается целиком.        │
│ Имеет: кейстор, ключ в mlock/memfd_secret памяти.         │

│ Сеть: не нужна (в пределе — отдельный контейнер           │
│       с `--network none`: физически не может слить ключ). │
└───────────────────────────────────────────────────────────┘
        Секрет входит ОДИН раз при старте B и исчезает из мира A.
```

## 5. «Паспорт»: чем реально доказывается личность (честная таблица)

| Форма | Крадётся копированием файлов? | Устоит против вируса под тем же uid? | Годится headless? | Что реально доказывает |
|---|---|---|---|---|
| (a) **Файл-ключ** (наивное «как ssh-key») | **Да, полностью** — криптографически это тот же пароль | Нет | Да | «У кого есть байты файла» |
| (b) **Привязка к чипу** (TPM/Secure Enclave) | **Нет** — ключ неэкспортируем, копия = бесполезный блоб | Нет (вор не украдёт, но **воспользуется**, пока резидентен) | Да | «Эта машина согласна подписывать» |
| (c) **Хеш кода** (IMA/IPE/fs-verity) | Н/п | Нет (инъекция в память невидима) | Частично | «Это те самые байты программы» — но слепо к Python-скриптам; IPE-дока ядра прямо называет себя непригодной для general-purpose |
| (d) **uid/путь звонящего** (SO_PEERCRED — **kernel-truth**) | Н/п — ядро вычисляет заново на каждый connect, подделать нельзя | Нет, если вирус под тем же uid | Да, бесплатно | «Какой Unix-принципал постучался» |
| (e) **Человек** | Н/п | **Да — единственное, что бьёт** | **Нет по определению** | «Живой человек подтвердил именно это» |

**Вывод по «паспорту»:** максимум без облака и без человека = **(b) + (d)**: ключ
некопируем (чип), и он используется только по просьбе процесса, которого опознало ядро.
Голый файл-ключ (a) — не паспорт, а тот же пароль в профиль; это прямой ответ на
исходную формулировку.

**Чего в индустрии нет:** MCP-спека 2026-07-28 для stdio-транспорта прямо говорит
клиентам «retrieve credentials from the environment» — и всё. A2A Signed Agent Cards,
AP2, Okta/Auth0/Entra/AWS AgentCore — все решают «агент в облаке доказывает себя чужому
облаку». **Локальный агент, доказывающий себя своей же машине, не закрыт никем.**
SPIFFE/SPIRE даёт правильный *паттерн* (короткоживущий SVID выдаётся заново по
kernel-фактам uid+path, а не читается с диска как вечный bearer), но как инфраструктура —
оверкилл для одной машины (два демона + CA); десктоп-прецедентов не найдено.

## 6. Механика: что kernel-truth, а что декорация

**Kernel-truth (нельзя обойти из userspace):**
- `SO_PEERCRED` — uid/gid/pid фиксируются ядром в момент `connect()`; **но ценность
  появляется только если A и B реально под разными uid** — иначе проверка вырождается
  в «это я?».
- `SO_PEERPIDFD` (Linux ≥6.5) — атомарный pidfd того же пира; закрывает гонку.
  **Антипаттерн:** брать голый pid и потом читать `/proc/<pid>/exe` — открытая
  TOCTOU/pid-reuse проблема (живой баг ssh-tpm-agent#126, 2026-05; на macOS тот же
  класс — CVE-2026-24067). pid — только для логов.
- `seccomp` allowlist + `PR_SET_NO_NEW_PRIVS` — после установки фильтр неотключаем.
  Эталон: OpenSSH `sandbox-seccomp-filter.c`, deny-by-default, ~30 сисколлов, 567 строк.
- `Landlock` (ABI9 в ядре 7.1) — непривилегированная файловая изоляция процессом самого
  себя. Честно: ни OpenSSH, ни systemd, ни Firefox его для этого не применяют — реален,
  но пока не мейнстрим.
- `memfd_secret` (Linux ≥5.14, default-on с 6.5) — память вне линейного отображения ядра:
  не читается даже root через `/proc/kcore`, не попадает в core dump, не свопится.
  **Проверено сегодня по живым JSON: разрешён в дефолтных seccomp-профилях и podman
  (`containers/common`), и docker (`moby/profiles`)** — кастомный профиль не нужен;
  ограничение только версия ядра **хоста** ⇒ обязателен рантайм-фолбэк на mlock при ENOSYS.
- Отдельный PID namespace (если подписант — свой контейнер) — ptrace через границу
  невозможен **независимо от uid**. Самая крепкая стена из доступных.

**Декоративное (нужное, но не граница):** права 0600 на файл сокета (ограничивают, кто
*может* постучаться, но не говорят, *кто* постучался); каталог сокета — не в общем `/tmp`
(урок OpenSSH 10.1, 2025-10-06: переехали в `~/.ssh/agent/` именно потому, что
песочницы с доступом к `/tmp` «ambiently» получали доступ к ключам).

**Обязательное хардненинг-дополнение:** `PR_SET_DUMPABLE=0` + дроп `CAP_SYS_PTRACE` +
Yama `ptrace_scope` — иначе root в том же namespace читает память подписанта.

Плюс `PR_SET_DUMPABLE=0` для core | ~2 строки + тест | Пароль исчезает из `/proc/environ` приёмной и gateway. Ноль структурных изменений, ноль ломки 900 установок |
| **1. Вынести подписанта** | Новый `rustok-signer` (Rust): владеет кейстором и ключом; core/gateway ходят к нему за подписью через AF_UNIX; проверка `SO_PEERCRED`. Развёртывание — развилка §9 | 2–4 недели | Взлом приёмной больше не даёт сида. Появляется настоящая, ядром охраняемая граница |
| **2. Запереть подписанта** | `no_new_privs` + seccomp allowlist + Landlock + `memfd_secret`/mlock + ptrace-хардненинг; при отдельном контейнере — `--network none` | 1–2 недели | Даже взломанный подписант не может ни слить наружу, ни быть прочитанным соседями |
| **3. Паспорт + доказательства** | TPM-тир из ADR (ключ некопируем) + Kani-харнессы: парсер запроса тотален, no-panic, «секрет не попадает в выходной буфер» | 3–6 недель | (b)+(d) паспорт целиком; честные формулировки уровня «model-checked parser» |
| **4. Дальняя** | Выделенное устройство-подписант (Microkit/seL4, отдельный SKU — путь Kry10/HENSOLDT) **или** облачный тир с настоящей аппаратной аттестацией (AWS Nitro Enclaves / Azure ACI confidential — покупается уже сегодня) | — | Для серверных агентов — hardware-rooted паспорт; для параноиков — физически отдельный сейф |

## 8. Что это даёт и чего НЕ даёт (без прикрас)

| Сценарий | Сегодня | После Фаз 1–2 |
|---|---|---|
| Кража файлов (бэкап volume, синк дотфайлов, копия диска) | Сид + пароль рядом → всё | То же (лечится Фазой 3 / TPM), **но** пароля нет в env |
| Взлом Python-MCP (prompt injection, злая зависимость) | Читает пароль из своего env + кейстор с диска → **сид навсегда, молча** | Может только **просить подписи**, пока резидентен. Сид недостижим. Каждая просьба — on-chain след |
| Взлом gateway | То же | То же, что выше |
| Вирус под тем же uid, что подписант | Всё | **Всё.** Честный предел: ядро правдиво скажет «да, это тот самый принципал» — и будет бесполезно. Бьётся только (e) человеком, политикой внутри подписанта или аппаратной аттестацией |
| root на машине | Всё | Почти всё; `memfd_secret` — единственное, что специально спроектировано устоять против чтения root'ом |
| Физическая кража устройства | Вне скоупа продукта | Вне скоупа |

**Ключевой сдвиг, ради которого всё:** необратимая тихая кража (сид) превращается в
обратимый шумный доступ (просьбы о подписи). Это тот же выигрыш, что privsep дал
OpenSSH в 2003-м: конкретные CVE понизились с «unauthenticated remote root» до «no
privileges» — не потому, что дыры исчезли, а потому, что за дырой оказалась стена.

## 9. Решения по развилкам (приняты 2026-08-02)

### 9.1. Развёртывание — РЕШЕНИЕ КАПИТАНА: отдельный контейнер

Подписант — **самостоятельный долгоживущий контейнер**: `--network none` (физически не
может ничего слить наружу даже будучи взломанным), собственный PID-namespace (ptrace
через границу невозможен **независимо от uid** — самая крепкая доступная стена),
собственный не-root uid, `--read-only` корень + tmpfs. Канал — unix-сокет в общем
volume; агентский контейнер остаётся эфемерным (`--rm`) и запускается MCP-клиентом
как сейчас. Цена принята: install.sh поднимает два юнита вместо одного.

Отвергнутая альтернатива (один контейнер, разные uid) требовала бы root-entrypoint с
последующим `setpriv` — регресс свойства «образ не работает от root», которое проверяют
сканеры ClawHub, и слабее по стенам (общий PID-namespace).

**Живая проверка (podman 5.8.4, Fedora, rootless, 2026-08-02) — схема подтверждена:**
сокет в именованном томе работает между двумя контейнерами; у сейфа с `--network none`
исход наружу реально закрыт (`OSError: [Errno 101] Network is unreachable`); агент видит
в общем томе только `s.sock` и ничего больше; **`SO_PEERCRED` через границу контейнеров
возвращает настоящий uid** (клиент под uid 0 → сейф видит 0; под uid 1001 → видит 1001).
Найдено ограничение: **pid через границу не виден** (`pid=0` — разные PID-namespace),
значит опознание «какая программа» между контейнерами невозможно в принципе — паспорт
сводится к «какой пользователь» + «кому вообще выдан монтаж тома». Конструкцию на pid не
строить (что и так следовало из TOCTOU). Обязательное правило: сокет **только в
именованном томе**, никогда в bind-mount с хоста — через границу «macOS/Windows ↔
виртуалка» unix-сокеты не проходят (требует живой проверки на маке).

**Поправка о цене фоновой службы (Капитан, 2026-08-02).** Формулировка «постоянная служба
= трение для пользователя» — неверна: аудитория автономного агента уже держит
контейнеры и службы запущенными (норма экосистемы — `NVIDIA/NemoClaw` позиционируется
буквально как «always-on local AI agent»), а для серверного автономного агента постоянный
процесс — естественная форма, а не уступка. **Настоящая цена — инженерная, не
пользовательская**, и она наша, а не их: (1) впервые в продукте появляется объект, чьим
жизненным циклом владеет пользователь/инсталлер, а не MCP-клиент; (2) новый класс отказа —
рассинхрон версий агент↔сейф (сегодня невозможен, один образ) ⇒ обязателен version-handshake
и именованная ошибка; (3) автозапуск: на docker `--restart unless-stopped`, на rootless
podman — quadlet/`podman-restart.service` **плюс `loginctl enable-linger`**, иначе служба
умирает при выходе пользователя; (4) «обновил образ, но не пересоздал контейнер» —
классическая ловушка; (5) update/uninstall-поток (`.claude/specs/2026-07-20-pr2.3c-update-uninstall.md`)
переписывается; (6) «сейф не запущен» обязано быть мгновенной именованной ошибкой, не
30-секундным висяком (урок Ф-1).

**Недооценённый плюс:** постоянный сейф разблокирует ключ **один раз**, а не на каждую
MCP-сессию — сегодня каждый запуск платит Argon2id 64 MiB/3 итерации
(`core/crates/keyring/src/encryption.rs:34`) плюс ожидание готовности core/gateway. Кроме
того, «один сейф — много агентов» физически невозможен для эфемерного per-session
контейнера, то есть постоянная форма — **предпосылка** отдельного универсального продукта (§9Б).

**Честный контр-довод (принят, компенсируется):** ключ теперь лежит расшифрованным в
памяти постоянно, а не только на время сессии — окно экспозиции растёт. Именно поэтому
хардненинг памяти из Фазы 2 (`memfd_secret`/mlock, `PR_SET_DUMPABLE=0`, отсутствие сети,
недостижимость ptrace через PID-namespace) в этой схеме **не опция, а обязательное
условие**, а не «приятное дополнение». Опционально — idle-lock по таймауту (требует
повторной доставки пароля, поэтому в v1 не закладываем).

### 9.2. Политика внутри подписанта — РЕШЕНИЕ: механизм есть, по умолчанию пуст

Три уровня, разделённые намеренно:

1. **Структурная валидация — ОБЯЗАТЕЛЬНА и это НЕ ограничение автономии.** Подписант
   обязан понимать, что подписывает: принимаются только декодируемые полезные нагрузки
   (EIP-1559/legacy tx, EIP-712 typed data, EIP-191 personal message) и **отвергается
   слепая подпись непрозрачного 32-байтного дайджеста**. Причина — известный класс атак:
   «подпиши безобидный хеш», который на деле хеш транзакции. Прецедент в нашем же
   продукте: `sign_message` уже отклоняет hex-блобы и payload >4 KiB. Это принцип
   «понимай, прежде чем подписать», а не «лимит».
2. **Policy-движок — присутствует, дефолт `allow all`.** Обоснование: (а) встроить
   правила в «коронную драгоценность» потом — значит снова трогать и заново верифицировать
   самый чувствительный компонент; (б) сейчас это дёшево, потом дорого; (в) для
   универсального продукта (§12) policy — обязательный минимум, без него компонент
   несерьёзен для любого корпоративного интегратора; (г) обещание «без ограничений»
   не нарушено: файл политики пуст, правила пишет только сам пользователь.
   Отличие от эталона (Clef): при несовпадении хеша файла политики Clef **тихо**
   откатывается на ручное подтверждение — у нас человека нет, поэтому **инвертируем:
   mismatch = hard fail**.
3. **Аудит-лог с hash-chaining — обязателен.** Append-only + цепочка хешей (Clef этого
   не делает, его лог не tamper-evident). Это и есть «видимость без ограничения»: полный
   локальный след всех просьб и решений, ничего не запрещающий. Именно тот паттерн,
   которого не нашлось on-chain.

### 9.3. Уровень доказательств — РЕШЕНИЕ: L1+L2+L3, крипто = k256

**Крипто-зависимость: `k256` (RustCrypto)** — решено фактом из кода: ядро уже на нём
(`core/crates/crypto/Cargo.toml:19`, `k256 = "0.13"`, features `ecdsa`), плюс
`alloy-consensus` с фичей `k256` в `crates/sign`. Аргументы совпадают: чистый Rust без
C-FFI (Kani не видит внутрь C — примешивать C в минимальный TCB, который мы собираемся
доказывать, бессмысленно), аудит NCC Group E008526 (2023-08-25, найденные high-severity
исправлены), консистентность с ядром. Отвергнут `libsecp256k1` — обстрелянность выше,
но ценой unsafe-FFI границы внутри доказываемого компонента и расхождения с ядром.

**Обязательная лестница:**
- L1: `cargo-fuzz` на парсер провода + `Miri` в CI.
- L2: Kani-харнессы на три свойства — (1) парсер запроса тотален (никаких паник и
  переполнений для любого входа до N байт); (2) инвариант конечного автомата: подпись
  не выдаётся ни на одном пути, минующем аутентификацию вызывающего и политику;
  (3) секрет никогда не попадает в выходной буфер. Образец — Firecracker: харнессы
  ставят точечно на компоненты «на границе с недоверенным», без цели «доказать всё».
- L3: k256, без самодеятельности в крипто.

**Формулировки — что можно и что нельзя.** Можно: «model-checked request parser»,
«panic-freedom proven for bounded inputs», «audited crypto (k256, NCC Group 2023)»,
«minimal TCB, readable end-to-end». **Нельзя никогда**: «formally verified wallet/signer»
— полностью верифицированного secp256k1 ECDSA не существует ни у кого в мире
(проверено: s2n-bignum покрывает только полевую арифметику и операции над точками).
Отдельное напоминание из свежего прецедента: в верифицированной libcrux в феврале 2026
нашли 3 бага — «можно доказать теорему и всё равно уронить сервер».

## 9А. Иммунные механизмы: что берём и от чего природа сама отказалась

Идея Капитана («лейкоциты отличают своё от чужого») указала на верную **проблему**, но
на отвергнутый **механизм** — и это подтверждается историей самой иммунологии.

**Почему self/non-self не наш путь.** Наша угроза — компрометация внутри легитимного
процесса — структурно тождественна **нецитопатической вирусной инфекции** (вирус живёт
в клетке, не убивая её и не искажая её удостоверение). Это канонический пример, который
модель «своё/чужое» объясняет плохо и ради которого Мацингер предложила теорию
опасности (1994, Science 2002). Компьютерная наука повторила ту же ошибку независимо:
«искусственные иммунные системы» с негативной селекцией (Forrest, 1994) в проде не
прижились — ни один современный рантайм-инструмент (Falco, Tetragon, Tracee, KubeArmor)
их не использует, все они движки правил. **Вывод: механизмы, ищущие «чужого», для нашей
модели угрозы — тупик по построению, а не по недоработке.**

**Что выжило из этой родословной и работает сегодня:** «выучи форму нормального в
доверенном окне» — AppArmor (происходит буквально от проекта **Immunix**, 1998-2003),
SELinux permissive + `audit2allow`, автогенерация seccomp-профилей из наблюдения
(`oci-seccomp-bpf-hook`). Прямой предок — Forrest, «A Sense of Self for Unix Processes» (1996).

**Переносим (6 механизмов):**

| Биомеханизм | В подписанте | Прецедент |
|---|---|---|
| **Костимуляция** (сигнал 1 + независимый сигнал 2; при одном сигнале — анергия, не атака) | Синтаксически валидный запрос от опознанного ядром процесса = только сигнал 1. Сигнал 2 обязан приходить из канала, структурно недоступного компрометации той же машины | two-man rule, MFA, threshold-подпись |
| **Сигналы опасности** (реакция на повреждение, не на чужеродность) | Канареечные объекты в окружении агента + контекстные аномалии как триггер, не привязанный к личности спрашивающего | canarytokens, honeypot |
| **Врождённый + адаптивный слоями** | Дешёвые always-on проверки (структурная валидация, rate-limit) + дорогая точная проверка только при превышении порога риска | — |
| **Анергия vs апоптоз** (разная обратимость) | Градация: по умолчанию обратимая блокировка, необратимое стирание ключа — только по событию высокой уверенности | TPM 2.0 anti-hammering (32 попытки, прощает 1 в 10 мин) vs HSM tamper-zeroization |
| **Обучение формы запросов** (не личности вызывающего) | Профиль обычных транзакций, собранный в доверенном окне провижининга | AppArmor complain→enforce |
| **Пороговая множественность** | Кворум как инженерная реализация сигнала 2 | threshold-ECDSA, multisig |

**Честные цены:** (1) по-настоящему независимый сигнал 2 требует **другой машины** —
второй процесс на том же хосте падает вместе с первым, это иллюзия; (2) kill-switch даёт
прямой аналог аутоиммунного заболевания — ложное срабатывание = самосаботаж, и противник
может триггерить его нарочно; поэтому дефолт — обратимая блокировка с путём восстановления.

**Не строить на этом (проверено, связи нет):** «ДНК-репарация вдохновила ECC» — легенда
без родословной; «quorum sensing → Paxos/Raft» — совпадение термина; N-версионное
программирование слабее, чем звучит (Knight & Leveson, 1986: ошибки «независимых»
команд коррелируют). Отдельным проектом это не является — это свойства подписанта.

## 9Б. Вынос в отдельный проект: РЕКОМЕНДАЦИЯ «ДА» (решение о публикации — за Капитаном)

**Вакуум подтверждён с двух сторон:** (1) карта рынка агентской безопасности 2026
(20+ вендоров, $3.6 млрд) прямо констатирует, что **никто** не занимается
криптографической подписью / custody приватных ключей для агентов; (2) ~~в официальном
каталоге MCP-серверов нет ни одного wallet/signing-сервера~~ — **ЛОЖНОЕ УТВЕРЖДЕНИЕ,
опровергнуто 2026-08-02**: живой запрос к `registry.modelcontextprotocol.io` возвращает
наш собственный `io.github.rustok-org/rustok-wallet` в трёх активных версиях
(0.4.0/0.4.1/0.4.2) плюс `io.github.temrjan/rustok-wallet` 0.2.2. Правильное прочтение
факта: мы в каталоге есть и мы невидимы — это диагноз **воронки**, а не подтверждение
ниши. Утверждение попало в документ из отчёта субагента без личной проверки; (3) прямого аналога
нашей комбинации (контейнер без сети + свой PID-namespace + unix-сокет + аутентификация
вызывающего ядром) найти не удалось — существующие remote-signer'ы (Web3Signer, Dirk,
Clef, EIP-3030) заточены под валидаторов/BLS и сетевую mTLS-модель, причём EIP-3030
(статус Stagnant) **явно выносит аутентификацию за скобки**.

**Стратегическая рамка — не «кошелёк для NVIDIA», а недостающая деталь их же истории:**
- `NVIDIA/OpenShell` (Rust, Apache-2.0, 7945★, 1128 форков, коммиты активны на 2026-08-01;
  проверено напрямую через GitHub API) — «safe, private runtime for autonomous AI agents»,
  контейнерная изоляция + policy-egress. Его README: *«Credentials never leak into the
  sandbox filesystem; **they are injected as environment variables at runtime**»* — это
  ровно тот антипаттерн, который мы убираем у себя на Фазе 0.
- Их собственная AI Red Team (2026-07-30, Harang & Lynch): *«**Never make persistent
  secrets accessible to an agent**»*, *«a **token broker** that provides least-privilege,
  ephemeral tokens should be used»*, и — важнейшее для нашего тезиса — *«Defenses in the
  same control plane as the LLM… are routinely subverted»*, нужны *«deterministic
  architectural controls **outside the model's control plane**»*.
- У NVIDIA **ноль** в agent payments/wallets/crypto (проверено целевым поиском) — значит
  заходить надо языком «securing agent runtime», а не «агентские платежи» (там AWS
  AgentCore уже в GA, плюс Coinbase/Privy).
- Формула позиционирования: **OpenShell изолирует то, что агент может делать; подписант
  убирает то, что имеет смысл красть.**

**Интерфейс — два слоя (решение):**
1. **Ядро:** JSON-RPC 2.0 по unix-сокету со словарём Ethereum (`eth_signTransaction`,
   `eth_signTypedData_v4`, `personal_sign`) — паттерн, проверенный Clef; минимален, не
   тянет HTTP-стек.
2. **Верх:** **один** MCP-сервер как тонкая обёртка — единственная абстракция, которую
   нативно понимают Claude/ChatGPT/Cursor и которую как pass-through поддерживают
   Coinbase AgentKit, NVIDIA NeMo Agent Toolkit и AutoGen.
   **Отвергнуто:** PKCS#11 и KMIP (ни один агентский фреймворк их не понимает нативно;
   вдобавок AWS CloudHSM PKCS#11 **не поддерживает secp256k1** — только NIST-кривые).

**Анти-GOAT-оговорка (главный риск и его нейтрализация).** GOAT SDK — концептуально
ближайший предшественник (MIT, «один слой на все фреймворки») — **архивирован** без
названного преемника. Диагноз: его ценностью была *широта интеграций* — беговая дорожка
из N адаптеров под постоянно меняющиеся API. Наша ценность — **свойство безопасности**
(ключ недостижим, вызывающий опознан ядром, песочница, доказанный парсер), которое не
протухает при смене API LangChain. Поэтому правило: **ровно один агентский адаптер (MCP),
и мы принципиально не поддерживаем N фреймворк-адаптеров** — обёртка над сокетом пишется
любым желающим за ~50 строк.

**Отношения с кошельком:** не два продукта, а продукт и извлечённая из него коронная
драгоценность — как `libsecp256k1` для Bitcoin Core. Кошелёк становится первым
потребителем подписанта.

**Лицензия: Apache-2.0** — доминирует ровно в этой нише (Web3Signer, Dirk, tmkms, SPIRE,
cosign, AgentKit, NeMo Agent Toolkit), плюс патентный грант, релевантный для крипто.

**Образцы для копирования модели доверия:** `tmkms` (Rust, Apache-2.0, изолированный
HSM-backed подписант отдельным репо — архитектурно ближайший, наш стек);
`yubikey-agent` / `ssh-tpm-agent` (маленький демон, простота как аргумент доверия);
`Clevis/Tang` (философия «минимальный демон, отвечающий на один криптозапрос, без
escrow»); `SPIRE` (путь к настоящему аудиту — через фонд: CNCF оплатил им Cure53).

**Нейминг — за Капитаном (бренд, наружу, необратимо).** Занято во всех реестрах:
citadel, keep, vault (HashiCorp/IBM), sentry (Sentry.io), signer — причём крейт `signer`
= `qntx/signer`, «Multi-chain transaction signer», создан 2026-06-16, прямой конкурент по
имени и домену. Проверка 2026-08-02: на npm свободно `keyward`; `signet`/`sigil`/`custos`/
`redoubt`/`thymus` заняты; crates.io проверить не удалось (403 анти-бот) — требует
перепроверки перед выбором. GitHub-организации с этими именами заняты, но репозиторий

### ИМЯ ПРИНЯТО: `neversig` (решение Капитана, 2026-08-02)

Капитан убрал `n` из `neversign` → **`neversig`**. Проверка того же дня — **чистый прогон,
лучший за всю сессию**: crates.io, npm, PyPI, GitHub-организация — всё **свободно**;
репозиториев с таким именем — 1 (`burhanuddinlaw-source/NeverSignBlind`, тематический
сосед, не конкурент); домены `.com/.dev/.io/.sh/.app` — все свободны, причём `.com`
подтверждён **whois'ом**: `No match for domain "NEVERSIG.COM"` (не зарегистрирован, а не
просто без DNS).

Почему усечение — улучшение, а не косметика: (1) **снимает моё главное возражение** —
фраза «never sign» конкурирует в поиске с горой предупреждающего контента Ledger/MetaMask,
а `neversig` — уникальный придуманный токен, ранжируется сам за себя с первого дня;
(2) короче (8 букв), уходит неудобный кластер «gn» на конце; (3) `sig` — родная
аббревиатура этого поля (`sigstore`, `sigsum`, файлы `.sig`), читается как язык своих,
а не как обрубок; (4) владение `.com` придуманного слова — реальный актив для выхода
на корпоративную аудиторию.

Единственный минус и его лечение: **опечаточный налог** — на слух люди напишут
`neversign`. Купить `neversign.dev`/`.io` (сам `neversign.com` занят) и поставить редирект
одновременно с основным доменом.

Слоган остаётся из синтеза ниже: **«your agent never signs — it asks»**.

---

*Предыдущая рекомендация (перекрыта решением выше, сохранена для истории):* имя `sigkeep`,
слоган «your agent never signs — it asks».
Короче (7 букв), читается однозначно (SIG-keep), все три домена свободны (единственный
такой), организация GitHub свободна, шум почти нулевой. Провокация переезжает в слоган,
где её можно объяснить, а имя остаётся коротким и ищущимся. Дополнительный
стратегический плюс: попадает в семью имён supply-chain-подписи (`sigstore`, `sigsum`),
а NVIDIA-Verified Agent Skills уже стоит на OpenSSF Model Signing — то есть имя звучит
для целевой аудитории «своим». Риск: возможное прочтение как производного от sigstore.

Независимо от выбора имени: история Перстня рыбака (камерленго разбивает папскую печать
молотком, чтобы никто не подписал от имени умершего) — готовая иллюстрация для доков к
функции стирания ключа; Аль-Хазне (`khazneh`, всё свободно, включая .com/.dev/.io) —
запасной вариант с сильнейшей историей «все видят, никто не вскроет».

**Открытие исходников — отдельное решение Капитана.** Ядро приватно по решению
2026-07-11. Подписант не содержит IP ядра (нет txguard, RPC-слоя, MCP-инструментов
кошелька), но публикация — расширение периметра со своей моделью угроз, и её нельзя
протаскивать вместе с техническим дизайном. При этом честно: компонент, чья ценность —
«его можно прочитать целиком», закрытым бессмыслен, а NVIDIA подхватывает только
публичное с органическим трэкшеном (их каталог Blueprints — по приглашениям).

**Практические шаги, если «да»:** (1) заявка в NVIDIA Inception (бесплатно, без доли);
(2) публичный Apache-2.0 репозиторий с CLI-инсталлятором и docs — единственный формат,
который NVIDIA реально подхватывает; (3) нарратив как продолжение их же публикаций
(secrets-брокер + verified skills), а не как крипто-фича; (4) оценить мост к
`NVIDIA/attestation-sdk` (есть Rust-биндинги) — конкретная демонстрируемая стыковка.

## 10. Что из найденного трогает ратифицированные решения

- **Не трогает** (можно делать хоть завтра): Фазы 0–2 целиком, TPM-тир, Kani, память,
  песочница. Это защита *механизма*, не ограничение *автономии*.

  контейнер (§9.1б) — меняет воронку; облачный TEE-тир (Фаза 4) — трогает «без облака».
  Все три вынесены как развилки, а не заложены в дизайн.
